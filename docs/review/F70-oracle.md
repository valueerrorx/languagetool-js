# F70 / F71 oracle (X-SRV-EXEC, X-LOGS)
Status: DONE. All expected values come from the real Java jar (`oracle/java-src` distribution, env D-018, `npm run oracle -- X-SRV-EXEC|X-LOGS [<case>]`). Fixtures: `tests/golden/X-SRV-EXEC` (88 cases: 61 http, 21 cli, 6 harness), `tests/golden/X-LOGS` (41 cases: 20 http, 21 cli). Generators `oracle/scripts/gen-cases-srv-exec.mjs`, `gen-cases-logs.mjs`. Infrastructure and flags: `oracle/README.md` (last section).
Re-running the timing-sensitive cases (queue-*, timeout-*, pipeline-pool-exhausted) twice gave byte-identical responses.

## Determinism design (no wall-clock assertions)
- Timeouts: `maxCheckTimeMillis=0` (and 1..25 ms with a 11 KB text, 100..999 ms with a 56-112 KB text): `future.get(0)` always times out because the check has not finished. Servers with timeouts start with `pipelinePrewarming=true preferredLanguages=en-US,en-GB,de-DE,fr`: without it the cancel/interrupt of a cold start breaks a static initialiser (`NoClassDefFoundError: ... EnglishRepeatedWordsRule`) and later requests of that JVM fail at random (observed in the first run; Java race, not reproducible in the port).
- Queues: `maxTextCheckerThreads=1`, `textCheckerQueueSize=n`, slow requests = 56 KB clean text (1.8-3 s warm) started `stagger` ms apart (`{parallel:[...], stagger:150}`), result recorded in request order. The statuses depend only on "request A still runs while the others arrive". Rejected requests answer at once. A warm-up request precedes every burst.
- Concurrency without stagger: result is the sorted multiset of (status, body) (`concurrent-equal`).
- Limiter windows: `requestLimitPeriodInSeconds=3600` (or 2 s with a 2.6 s `sleep` for expiry).
- Every case has its own server JVM (`isolate`): counters `r`, `#n`, limiter events, caches start at 0.
- Ports: oracle servers 18300-18399 (`ORACLE_PORT_MIN/MAX`), fixed ports 18360-18399 for cli/harness servers (18360-18377 harness-crash-server, 18380-18387 X-LOGS cli-server-*, 18390-18394 X-SRV-EXEC cfgfail/limits cli).

## Normalisation (recorded raw; applied at compare time)

## Findings worth porting exactly
- Timeout 500 text uses `float` seconds and says "Checking took longer than 0.0 seconds, which is this server's limit..." (the handler's own text, since the exception message starts with "Text checking", not "Checking took longer"); the exception message itself (cancelled/lang/detected/#n/h/r/requestId/load) only shows in logs.
- `maxWorkQueueSize` 503 body has a doubled prefix: `Error: Error: There are currently too many parallel requests. Please try again later.` (healthcheck: `Error: Healthcheck failed: ...`).
- `textCheckerQueueSize` 0 = unbounded; healthcheck fails when queue size > size/2 (integer division).
- `maxTextHardLength=40` answers "hard limit of 400 characters" and accepts 41 chars (factor 10 in the Java check).
- ruleValues without `:` -> 500 "Internal Error: Index 1 out of bounds for length 1"; `language` missing -> 400 text; `username` with `apiKey` -> 403 AuthException text; empty `username` -> 500 "username must be set".
- `maxCheckTimeMillisPremium`/`LoggedIn` are unknown config keys (stdout warning) but read.
- Requests of kind log-my-IP get no HTTP response (connection closed, log line "sending code -1").
